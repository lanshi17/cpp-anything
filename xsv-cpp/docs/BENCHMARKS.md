# Benchmark design

## 1. Questions

| id | hypothesis | primary metric | decision rule |
| --- | --- | --- | --- |
| H1 | optimized parsing raises throughput | rows/s, MB/s | median ratio with 95% CI, `base` vs `all` |
| H2 | custom memory management lowers cost | peak RSS, allocation count | RSS ratio; heap profile attribution |
| H3 | parallelism shortens large jobs | wall time, scaling efficiency | 1→32 thread curve |
| H4 | SIMD lowers CPU work | cycles/row, instructions/row, IPC | `perf stat` delta at equal wall time |
| H5 | complex operations gain the most | sort/join/stats wall + RSS | per-command ratios |
| H6 | behaviour is preserved | differential pass rate | 100% required before any number is reported |
| H7 | gains justify engineering cost | dev-days, LOC, build time, deps | reported, not scored |

The report must allow “C++ loses” and “the gain came from the algorithm, not the
language”.

## 2. Datasets

Generated by `scripts/generate_datasets.py`; every file has a manifest with
rows, columns, seed, distribution, byte size and SHA-256.

| id | name | shape | purpose |
| --- | --- | --- | --- |
| D1 | `small_uniform` | 100k × 10 | startup, per-record overhead |
| D2 | `medium_uniform` | 1M × 20 | routine processing |
| D3 | `large_uniform` | 10M × 30 | throughput and RSS |
| D4 | `xlarge_uniform` | 100M × 30 | scale (opt-in; ~38 GB, exceeds 30 GB RAM for a whole-file copy) |
| D5 | `complex` | 5k × 12 plus handcrafted edge files | parser correctness |
| — | `high_card` | 1M × 10, 1M distinct keys | hash/aggregation |
| — | `low_card` | 1M × 10, 8 distinct keys | duplicate chains |
| — | `skewed` | 1M × 10, Zipf-like | hash clustering |
| — | `null_heavy` | 1M × 10, 80% empty | null policy |
| — | `wide_rows` | 100k × 8, 1–4 KiB fields | copies, cache misses |
| — | `sort_random/sorted/reverse/dupes/long` | 1M × 3 | sort algorithm behaviour |
| — | `join_left/right` | 1M × 5 / 100k × 5; full: 10M / 1M | hash join |

`complex` includes: UTF-8 multibyte, embedded CRLF, quotes and doubled quotes,
empty fields, duplicate header names, very long fields, BOM, no trailing
newline, ragged file (expected error), empty file.

The 100M × 30 file is ~38 GB. The `base` build reads the whole file into owned
memory and is therefore excluded from D4 (30 GB host). D4 covers count, index,
select, search, stats and slice; sorting and joining at this size exceed the
memory budget and are documented as not run.

## 3. Formal tests

`v1.0` covers the P0 commands. B08/B09/B11/B12 are defined now and run only
after the corresponding P1 command passes its own differential gate; they are
reported separately and never mixed into P0 conclusions.

| id | command | datasets | metric | status |
| --- | --- | --- | --- | --- |
| B01 | `count` | D1, D2, D3, D4 | rows/s, wall | P0, implemented |
| B02 | `index` | D2, D3, D4 | MB/s, wall, index size | P0, implemented |
| B03 | `select 1,10,20` | D2, D3, D4 | MB/s, wall | P0, implemented |
| B04 | `search <literal>` | D2, D3, D4 | rows/s, wall | P0, implemented |
| B05 | `sort -s 1` (5 orders), `sort -N -s 2` | D2, D3 | wall, peak RSS | P0, implemented |
| B06 | `join` inner/left/right/full/cross | 1M×100k; 10M×1M | wall, peak RSS, probes/key | P0, implemented |
| B07 | `stats` default; `--everything`; `-j` | D2, D3, D4 | rows/s, wall | P0, implemented (parallel with index) |
| B08 | `frequency` | D2, D3 | wall, RSS | P1, deferred |
| B09 | `sample` | D2, D3 | wall, RSS | P1, deferred |
| B10 | `slice -s K -l 100` | D2, D3 | latency, indexed vs not | P0, implemented |
| B11 | `partition` | D2, D3 | MB/s | P1, deferred |
| B12 | `fmt` | D2, D3 | MB/s | P1, deferred |

Additional P0 paths measured because they are where the design claims gains:

- `count` with a warm index (metadata only) vs full scan;
- `stats` with `-j 1/2/4/8/16/32` on an indexed D3;
- `join` on uniform, duplicate-heavy, skewed and null-heavy keys. The standard
  join corpus uses a key space four times the smaller table so the output is
  bounded (~250k rows); a cube-skewed 1M×100k pair would otherwise emit ~97M
  rows per run and measure output volume rather than join construction;
- parser-only microbenchmark (`XSV_BUILD_MICROBENCH=ON`) to separate I/O from
  parsing.

## 5. Execution protocol

For every (case, binary):

1. Validate dataset SHA-256 against its manifest.
2. Validate binary `--version` contains the expected variant.
3. Drop the page cache where permitted (`posix_fadvise(DONTNEED)`); record
   whether it worked.
4. 3 warmup runs (not recorded).
5. 20 measured runs minimum; runs are grouped in rounds; within each round the
   binary order is shuffled with a recorded seed.
6. Each run: fresh process, stdout to `/dev/null` (or a file when output is
   hashed), no shell, CPU affinity pinned when available.
7. Record wall time, exit status, CPU frequency before/after, package
   temperature, `loadavg`, and run index.
8. Peak RSS: separate `/usr/bin/time -v` pass; at least 3 runs, take the median.
9. One output-producing pass per case; hash stdout and any `-o` file and require
   equality across all variants.

Cold vs warm cache is an explicit dimension (`cache=cold|warm`); results are
never pooled across it.

The runner must refuse to write results when:

- the reference PIN is missing;
- the dataset hash differs;
- the environment fingerprint differs from the file's header;
- the binary exits non-zero on a case that is not marked as an error case.

## 6. Metrics

| metric | source |
| --- | --- |
| wall time | `time.perf_counter` around `posix_spawn` |
| rows/s, MB/s | rows or input bytes ÷ median wall time |
| peak RSS | `/usr/bin/time -v` → `Maximum resident set size`; mapped commands advise away 8 MiB windows |
| allocations | heaptrack, or PMR counters in-process |
| cycles, instructions, IPC | `perf stat -e cycles,instructions,cache-misses`; unavailable here (`perf_event_paranoid=4`) |
| CPU substitute | TSC cycles, user/system CPU seconds, faults and context switches from `tools/cpu_metrics.cpp`; no IPC claim |
| branch/cache behaviour | same `perf stat` run; unavailable here |
| thread scaling | `stats -j` / `join` with `XSV_THREADS=1..32` |
| build cost | `/usr/bin/time -v cmake --build`, dependency count, LOC |
| coverage | `gcovr`/`llvm-cov` not required; differential pass rate is the gate |

### CPU metrics when perf is blocked

`kernel.perf_event_paranoid=4` rejects even software events on the reference
host. `scripts/run_cpu_metrics.sh` therefore runs each binary under
`build/cpu-metrics`, which forks/execs the command and records `wait4` rusage
plus `__rdtsc` before/after. The report labels these as **CPU-side indicators**
(user/system seconds, effective TSC GHz, page faults, context switches, RSS),
not as hardware cycles or IPC. This is the documented substitute, not a
replacement for enabling perf on a dedicated runner.

## 7. Statistics

- Report median, P95, standard deviation and min/max.
- 95% confidence interval by 10,000 bootstrap resamples of the median.
- Paired comparison when the same round contains both binaries: Wilcoxon
  signed-rank; otherwise Mann–Whitney U.
- Effect size: ratio of medians with CI, plus absolute delta.
- A result is “reported” if the CI excludes 1.0; a result is “material” only if
  the ratio is outside 0.95–1.05 and the CI is narrower than that band.
- No p-value is computed for n < 20; the run is repeated instead.
- Outliers are not deleted. A run is excluded only for a recorded environmental
  event (OOM, thermal throttle, scheduler preemption above threshold), and the
  exclusion is listed in the raw file.

## 9. Threats to validity

- **Language vs algorithm.** Both the reference and `all` use a serial hash
  join; `all` replaces the map with a PMR-backed flat hash table. The join gain
  is therefore a data-structure/implementation result, not a parallelism or
  language result. `base` vs Rust is the language comparison; `all` vs `base`
  is the optimization comparison.
- **Page cache.** The second process in a pair benefits from the first's reads.
  Random order, warmups and an explicit cache dimension reduce, but do not
  eliminate, the bias.
- **Allocator.** Both sides use the system allocator by default; PMR changes
  allocation policy, not the underlying `malloc`.
- **Regex engine.** RE2 and Rust `regex` are different engines; `search`
  measures “engine + glue”, not language alone.
- **Compiler flags.** Portable vs `-march=native` is a separate axis; never
  compare native C++ to portable Rust.
- **Small files.** Startup dominates below ~1 MB; D1 is reported separately and
  not used for throughput claims.
- **Virtualized CI.** Formal numbers come from one fixed machine; CI numbers are
  smoke-only and labelled as such.
